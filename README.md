# Duskrun

Self-hosted резервное копирование разнородных СУБД. Один статический бинарник +
SQLite, плагинный стриминговый пайплайн `Connector → Dumper → Codec* → Storage`.

> Статус: **до 1.0**. Формат API и конфигов ещё может меняться между
> минорными версиями — изменения описаны в `CHANGELOG.md`.

## Требования

- Go 1.26+
- Внешние утилиты в окружении воркера: `pg_dump`, `mysqldump`, `mongodump`,
  `redis-cli` (проверяются при создании задачи, см. `duskrun doctor`).
- Для старых источников MySQL 5.6 и ниже duskrun автоматически ищет совместимый
  dump-клиент (`mysqldump56`, `mysqldump-5.6`, `mysqldump5.6`); если его нет,
  включает legacy fallback через `mysql` CLI без проблемного `generation_expression`.
- Для connector'а `docker-proxy`: Docker CLI + доступ к Docker daemon; образ
  `alpine/socat:latest` должен быть доступен локально или подтянут Docker'ом.

## Что поддерживается

| Движок | Утилита | Режим | Примечание |
|---|---|---|---|
| postgres | `pg_dump` / `pg_dumpall` | стриминг | форматы custom/plain/directory, дамп всего кластера |
| mysql | `mysqldump` | стриминг | fallback для MySQL 5.6 и ниже |
| mongodb | `mongodump --archive` | стриминг | пустая база = все базы инстанса; артефакт `.archive` |
| redis | `redis-cli --rdb -` | стриминг | RDB-снимок всего инстанса, базу указывать нельзя |

| Хранилище | Примечание |
|---|---|
| localfs | локальный каталог |
| s3 | S3-совместимое, потоковый multipart |
| sftp | по SSH, ключевая аутентификация, проверка host key (tofu/strict) |

Codec chain: `gzip`, `zstd`, `tar`, `age` (шифрование). Сжатие делает только
codec chain — дамперы не включают собственное сжатие, иначе суффикс в имени
артефакта врал бы.

**Redis:** RDB — это снимок на момент, а не транзакционно согласованная выгрузка
в смысле реляционных СУБД. Восстановление — операция на сервере: файл кладётся
на место `dump.rdb` и загружается при старте, командой клиента RDB не
разворачивается.

**MongoDB:** пароль не передаётся в argv (у `mongodump` нет переменной окружения
для него) — duskrun пишет его во временный файл с правами `0600` и отдаёт
`--config`, файл удаляется по завершении дампа.

**SFTP:** запись атомарная — файл заливается под временным именем и
переименовывается в конце, поэтому оборванная загрузка не оставляет короткий
файл под ключом артефакта. Промежуточные каталоги создаются, удаление
несуществующего ключа ошибкой не считается (иначе повторный проход очистки
падал бы). Аутентификация только по ключу: `private_key_ref` указывает на секрет
типа `ssh-key`. Host key проверяется тем же кодом, что и у ssh-туннеля
(`internal/sshx`): `tofu` запоминает ключ при первом подключении, `strict`
принимает только то, что уже в `known_hosts`; смена ключа сервера отвергается в
обоих режимах.

## Секреты в конфигах плагинов

Любой ключ конфига вида `<имя>_ref` резолвится ядром: значение секрета из
хранилища подставляется под ключ `<имя>` перед тем, как конфиг увидит плагин.
Так живут `private_key_ref` у ssh-коннектора, `access_key_ref`/`secret_key_ref`
у s3 и `password_ref`/`token_ref` у каналов уведомлений. Правила:

- инлайновое значение под `<имя>` имеет приоритет над ссылкой;
- вложенные объекты и массивы обходятся рекурсивно;
- ссылка на несуществующий секрет — ошибка прогона, а не пустая строка: пустой
  пароль превратился бы в анонимный вход и в непонятную ошибку доступа;
- резолвинг происходит и в очистке по retention, и при скачивании артефакта,
  поэтому хранилище с ключом в секретнице читается на всех путях.

## CI и релизы

- **CI** (`.github/workflows/ci.yml`) на каждый PR и push в `main`: `go mod tidy`,
  `go vet`, `go test -race` с покрытием, golangci-lint (`.golangci.yml`),
  govulncheck, `tsc` + vitest + сборка SPA, сборка Docker-образа со smoke-тестом
  (`duskrun doctor` видит все клиенты БД, `/healthz` отвечает) и dry-run goreleaser.
- **Заголовок PR** (`pr-title.yml`) обязан быть conventional commit: `feat: …`,
  `fix(api): …`, `feat!: …`. PR мержатся squash-ом, заголовок становится
  коммитом в `main`, из него считается версия.
- **Релиз** (`release.yml`) ведёт [release-please](https://github.com/googleapis/release-please):
  после мержа в `main` он обновляет PR «chore(main): release X.Y.Z» с
  `CHANGELOG.md`. `feat` поднимает минорную версию, `fix` — патч, `!` до 1.0 —
  минорную. Мерж этого PR создаёт тег `vX.Y.Z` и GitHub Release, после чего
  повторно гоняются проверки CI и собираются:
  - архивы `duskrun_X.Y.Z_{linux,darwin}_{amd64,arm64}.tar.gz` и `checksums.txt`
    (goreleaser, `.goreleaser.yaml`) с build provenance;
  - образ `ghcr.io/<owner>/<repo>` под `linux/amd64` и `linux/arm64` с тегами
    `X.Y.Z`, `X.Y`, `latest`, SBOM и provenance.
- **Dependabot** (`.github/dependabot.yml`) раз в неделю группами обновляет Go-,
  npm-, Docker-зависимости и actions.

Проверить подпись скачанного артефакта или образа:

```sh
gh attestation verify duskrun_X.Y.Z_linux_amd64.tar.gz --repo <owner>/<repo>
gh attestation verify oci://ghcr.io/<owner>/<repo>:X.Y.Z --repo <owner>/<repo>
```

## Аутентификация

Есть два независимых способа попасть в API; оба идут в одном заголовке
`Authorization: Bearer …`.

| Что предъявлено | Кто это | Права |
|---|---|---|
| `DUSKRUN_API_TOKEN` | машинная учётка | `admin`, сессия не создаётся |
| токен сессии | пользователь | по роли пользователя |

**Первый запуск.** Пользователей ещё нет, поэтому единственный вход — статический
токен: задайте `DUSKRUN_API_TOKEN` и войдите на вкладке «API-токен». Он остаётся
рабочим и дальше — им ходят скрипты и CI, и он же вытаскивает инстанс, если
администратор потерял пароль. Если не задан ни токен, ни один пользователь, API
отвергает всё и демон говорит об этом в лог при старте.

Первого администратора заводит CLI — пароль читается из stdin, а не из аргумента,
чтобы не осесть в истории шелла:

```sh
printf '%s' 'длинный-пароль' | ./bin/duskrun user add --email you@example.com --role admin --name 'Имя'
./bin/duskrun user list
printf '%s' 'новый-пароль'   | ./bin/duskrun user passwd --email you@example.com
```

`user passwd` завершает **все** сессии этого пользователя: у команды из шелла нет
своей сессии, которую можно было бы пощадить. Смена пароля через UI
(`POST /api/me/password`) наоборот сохраняет текущую сессию и гасит остальные.

### Роли

| Роль | Что доступно |
|---|---|
| `viewer` | только чтение: дашборд, история, логи прогонов, метаданные артефактов |
| `operator` | `viewer` + задачи, соединения, хранилища, запуск, ручная очистка, скачивание артефактов, тест каналов |
| `admin` | всё + пользователи, сессии, секреты, создание каналов, настройки |

Права проверяются **на сервере**, у каждого маршрута своя минимальная роль.
Скрытие кнопок в интерфейсе — удобство, а не защита. Скачивание артефакта — от
`operator`: «только чтение» означает «видеть, что бэкап случился», а не
«выгрузить копию боевой базы».

У канала уведомлений роль разделена не только по маршруту, но и по полям:
`operator` меняет `events` и `enabled` (это матрица «события × каналы»), а имя,
тип и конфиг — только `admin`. Конфиг канала называет и секрет (`password_ref`),
и хост, которому этот секрет предъявляется, поэтому право переписать конфиг —
это право отправить любой секрет из хранилища на выбранный сервер и прочитать
его открытым текстом из `AUTH PLAIN`. Создание и удаление канала были `admin`
именно поэтому; правка была обходом.

Последнего включённого администратора нельзя отключить, удалить или понизить —
API отвечает `409`, иначе инстанс остался бы без управления.

### Сессии

Пароли хранятся как argon2id (m=64 MiB, t=3, p=2; параметры и соль внутри самой
строки хеша, поднимаются без миграции). В таблице `session` лежит только
SHA-256 токена — дамп базы не даёт доступа к живым сессиям.

Сессия живёт 30 суток со скользящим продлением, но не дольше 90 суток от
создания. Отключение пользователя обрывает доступ немедленно, включая уже
открытый SSE-поток прогона. Список сессий и кнопка «Завершить» — на странице
«Настройки».

**Известный компромисс:** токен сессии хранится в `localStorage` и потому
уязвим к XSS. Альтернатива (`httpOnly`-кука плюс защита от CSRF) переписывает
весь клиентский транспорт; сейчас пользовательского HTML на страницах нет — весь
вывод идёт через React как текст.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DUSKRUN_DB_PATH` | `duskrun.db` | файл метаданных SQLite |
| `DUSKRUN_LISTEN` | `:8080` | адрес HTTP (API + встроенный SPA) |
| `DUSKRUN_WORKERS` | `4` | глобальный лимит воркеров |
| `DUSKRUN_LOG_FORMAT` | `json` | `json` или `text` |
| `DUSKRUN_API_TOKEN` | — | статический bearer-токен для `/api/*` (машинная учётка, права `admin`) |
| `DUSKRUN_TRUSTED_PROXY` | `false` | доверять `X-Forwarded-For` при троттлинге входа |
| `DUSKRUN_RETENTION_CRON` | `30 3 * * *` | расписание очистки; `off` или пустое значение отключает |
| `DUSKRUN_MASTER_KEY` / `_FILE` | — | мастер-ключ (взаимоисключающие) |

## Watchdog

Раз в минуту демон проверяет, у каких задач давно не было **успешного**
бэкапа, и порождает событие `watchdog`. Это отдельная от `failure` вещь: если
задача перестала запускаться вовсе (сломанный cron, выключенный планировщик,
упавший демон), об ошибке никто не сообщит — сообщать не о чем.

Порог задаётся полем задачи `watchdog_sec`:

| Значение | Поведение |
|---|---|
| `0` (по умолчанию) | выводится из cron: два пропущенных окна, минимум 1 ч |
| `>0` | явный порог в секундах |
| `-1` | watchdog для задачи выключен |

Автовывод берёт **наибольший** интервал среди запусков расписания на неделю
вперёд. Окно именно недельное: у `0 9-18 * * 1-5` внутри рабочего дня все
промежутки по часу, а реальные простои — 15 ч ночью и 63 ч на выходных — видны,
только когда в окно попадают суббота с воскресеньем.

Плотные расписания (`*/1 * * * 1-5` и подобные) не удаётся обойти запуск за
запуском — до пятничного вечера тысячи срабатываний. Для них используется
сканирование окна с шагом 10 минут: ожидание из точки сразу после срабатывания
и есть длина следующего промежутка, поэтому наибольшее найденное ожидание —
наибольший промежуток (занижение не больше шага, что несущественно на фоне
удвоения и пола в 1 ч).

Детали поведения:

- задача, у которой успехов не было ни разу, отсчитывается от момента создания —
  иначе никогда не работавший бэкап был бы навсегда освобождён от проверки;
- только что созданная задача не алертит, пока не выйдет за своё окно;
- выключенные (на паузе) задачи не проверяются;
- алерт отправляется **один раз на эпизод**: повтор возможен только после того,
  как успешный запуск закроет текущий эпизод. Состояние переживает рестарт
  демона (таблица `watchdog_alert`);
- задача, снятая с паузы, получает окно заново (`task.enabled_at`) — иначе она
  алертила бы в момент включения, не успев ни разу запуститься. Обычное
  редактирование включённой задачи окно не сбрасывает.

Текущий список — `GET /api/watchdog`; он же питает панель «Наблюдение» на
дашборде, поэтому панель и уходящие уведомления считают одно и то же. Панель
показывает именно устаревание: единичный упавший запуск в неё не попадает (для
этого есть KPI «ОШИБКИ 24Ч» и событие `failure`). Если эндпоинт недоступен,
панель честно пишет «не удалось проверить», а не «нет алертов».

## Уведомления

Канал — это настроенная строка (`telegram`/`webhook`/`smtp`/`log`), а не просто
имя плагина. Задача ссылается на каналы по имени в `notifiers`, а канал сам
объявляет, какие события пересылает — это и есть матрица «события × каналы».
Доставка происходит, когда задача ссылается на канал, канал включён и подписан
на это событие.

Секреты не хранятся в конфиге канала: любой ключ вида `<имя>_ref` резолвится в
`<имя>` в момент доставки. Токен Telegram-бота лежит в секрет-сторе, а в
конфиге остаётся только ссылка:

```json
{ "chat_id": "-1001234567890", "token_ref": "secret://telegram/ops-bot" }
```

Email-канал (`smtp`) шлёт по одному текстовому письму на событие:

```json
{
  "host": "smtp.corp.io",
  "port": 587,
  "tls": "starttls",
  "username": "duskrun@corp.io",
  "password_ref": "secret://smtp/ops",
  "from": "duskrun@corp.io",
  "to": ["ops@corp.io", "oncall@corp.io"]
}
```

`tls` — `starttls` (по умолчанию, порт 587), `implicit` (465) или `none` (25);
режим задаётся явно, а не угадывается по порту. Сервер, не объявивший
STARTTLS в режиме `starttls`, считается ошибкой: письмо не уходит открытым
текстом «на всякий случай». Транспорт — стандартный `net/smtp`, поэтому
поддерживается только `AUTH PLAIN`; сервер с одним лишь `AUTH LOGIN` вернёт
ошибку со списком заявленных механизмов. Пароль по нешифрованному каналу
`net/smtp` отдаёт только на `localhost` — конфиг с логином при `tls: none` и
удалённым хостом отклоняется сразу, а не в момент ночного алерта.

Проверить канал локально: `docker compose --profile demo up -d mailpit`,
хост `127.0.0.1`, порт `1025`, письма видны на <http://localhost:8025>.

Эндпоинты: `GET/POST /api/notifiers`, `PATCH/DELETE /api/notifiers/{id}`,
`POST /api/notifiers/{id}/test` и `GET /api/notifications` (журнал доставок).

Ссылочная целостность по имени канала держится с обеих сторон: удаление канала,
на который ссылается задача, возвращает `409` со списком задач, а переименование
каскадится в `task.notifiers`. Иначе задача молча перестала бы уведомлять.

`PATCH` заменяет строку целиком, но отсутствующие `events` и `enabled` берутся
из текущего значения — иначе обновление без этих полей расширило бы намеренно
суженную подписку на все события.

Если секрет всё же задан инлайном, а не через `_ref`, `GET /notifiers` вернёт
его как `••••` (маскируются поля `token`/`password`/`secret`/`key`/`auth`).
Клиент, делающий read-modify-write, отправляет маску обратно, и запись
восстанавливает по ней сохранённое значение — иначе правка соседнего поля
затёрла бы рабочий токен четырьмя точками.

Секрет, на который ссылается канал, защищён так же, как секрет соединения или
хранилища: `DELETE /secrets/{id}` вернёт `409` со списком ссылающихся сущностей,
включая каналы. Иначе алертинг умер бы там, где никто не смотрит — в пути,
который срабатывает только когда бэкап уже упал.

Конфиг канала проверяется конструктором самого плагина при сохранении: `smtp`
без получателей — это `400`, а не строка в списке, которая выглядит здоровой и
падает впервые в журнале доставок.

Кнопка «Тест» проводит событие тем же путём, что и настоящее: та же сборка
канала, тот же резолвинг секретов, та же запись в журнал. Зелёный результат
значит, что канал действительно работает, а не что конфиг разобрался.

## Очистка по retention

Демон раз в сутки (`DUSKRUN_RETENTION_CRON`) применяет политику каждой задачи:
`keep_last` и GFS объединяются — артефакт, который сохраняет любое правило,
остаётся. Удаление идёт сначала из хранилища, затем из каталога.

Политика задаётся на шаге «Хранение» в мастере и редакторе задачи:

```json
{ "keep_last": 14 }
{ "gfs": { "daily": 7, "weekly": 4, "monthly": 12 } }
```

GFS (grandfather-father-son) хранит **самый свежий артефакт в каждом из
последних N периодов**: суток, ISO-недель и календарных месяцев. Периоды берутся
из самих артефактов, а не из календаря: если бэкапы неделю не шли, `daily=7`
удержит семь последних суток, *в которые бэкапы были*, а не семь пустых суток.
Так политика не выкидывает всё разом после простоя. Три счётчика независимы,
`0` выключает свой период.

**В формах правила взаимоисключающие:** либо `keep_last`, либо GFS, либо «без
очистки». Выключенное правило показывает рабочие значения по умолчанию
(`14` и `7/4/12`), поэтому включение — один клик, а не заполнение полей. Выбор
«без очистки» означает, что артефакты задачи не удаляются никогда; форма об этом
предупреждает, а страница «Политики хранения» помечает такие задачи как
«не настроена».

**Движок при этом объединяет правила** (`core.Forget`): артефакт, который
сохраняет любое из них, остаётся. Политика с обоими правилами сразу
задаётся через API и работает как объединение — так выражается «последние 14
прогонов, что бы ни случилось, плюс месячный архив за год». Формы такую политику
показывают целиком, но при сохранении оставят одно правило и предупреждают об
этом заранее.

Отрицательные значения отвергаются с `400`: `Forget` читает любое значение `<= 0`
как «правило выключено», поэтому опечатка вроде `keep_last: -1` тихо отключила бы
очистку на задаче, за которой оператор считает её включённой.

Каждый артефакт удаляется из **того хранилища, куда он был записан**, а не из
текущего хранилища задачи: `PATCH /api/tasks/{id}` позволяет переехать на другое
хранилище, и старые артефакты остаются на прежнем. Удаление их «не там» прошло
бы молча успешно (и localfs, и S3 считают отсутствующий ключ уже удалённым) —
строка каталога исчезла бы, а файл остался навсегда.

Объекты, лежащие в хранилище, но отсутствующие в каталоге (orphan), только
пересчитываются и **не удаляются**. Поиск идёт по префиксам из фактических
ключей каталога плюс текущее имя задачи, поэтому переименование задачи не
скрывает то, что было записано под прежним именем.

Задача без настроенной политики (`retention: {}`) пропускается: пустая политика
означает «хранить всё», а не «удалить всё». На странице «Политики хранения»
такая задача помечена отдельно.

Один неудаляемый объект (object-lock, права) не блокирует задачу: он
пропускается с ошибкой в отчёте, а более старые артефакты за ним всё равно
обрабатываются. Строка каталога при неудачном удалении сохраняется — иначе
объект остался бы без единой ссылки на него.

Тот же проход подрезает журнал доставок (`notification`) до последних 5000
записей. Журнал пишется на каждое событие каждого канала, включая успешные
бэкапы, и больше его никто не удаляет: задача раз в пять минут с двумя каналами
даёт ~200 тысяч строк в год.

Ручной прогон — `POST /api/retention/sweep` или кнопка «Очистить сейчас». Он не
привязан к контексту HTTP-запроса (закрытая вкладка или таймаут прокси не рвут
очистку) и ограничен собственным таймаутом. Если очистка уже идёт, запрос
получает `409`, а не блокируется на всю её длительность.

## Структура

```
cmd/duskrun/          CLI + демон (единый бинарник)
internal/
  plugin/             контракты Connector/Dumper/Codec/Storage/Notifier + registry
  core/               доменная модель (Task/Run/Artifact/Secret) + движок (M2)
  store/sqlite/       метаданные + claim-очередь (WAL, один writer, BEGIN IMMEDIATE)
  config/  obs/       конфиг (master key из env/file), slog + маскирование секретов
migrations/           встроенные *.sql (embed.FS)
```

## Ключевые инженерные решения

- **CGo-free** весь стек → статический бинарник (`modernc.org/sqlite`,
  `klauspost/compress/zstd`, `filippo.io/age`, `aws-sdk-go-v2`).
- **Очередь на SQLite:** write-пул `MaxOpenConns(1)` + `_txlock=immediate`,
  claim через одно `UPDATE ... RETURNING` — «ровно один воркер на задачу»
  гарантируется частичным uniq-индексом `ux_run_active`.
- **Стриминг без временных файлов:** `exec → io.Pipe → io.TeeReader(sha256) →
  zstd → age → S3 multipart`; память `O(PartSize × Concurrency)`.
- **Секреты:** envelope encryption (per-secret DEK под мастер-ключом с `key_id`)
  — ротация мастер-ключа без простоя.

## Docker Compose-internal DB через SSH

Если СУБД доступна только внутри Docker Compose network и не публикует порт на
host, используйте connector `docker-ssh-proxy`. `duskrun` подключится по SSH к
Docker-хосту, там запустит временный proxy-контейнер и пробросит его обратно
локальным SSH forward'ом:

```json
{
  "ssh_host": "docker-host.example.com",
  "ssh_user": "deploy",
  "private_key_ref": "secret://ssh/docker-host",
  "network": "myapp_default",
  "target_host": "postgres",
  "target_port": 5432
}
```

На удаленном Docker-хосте host port не выбирается приложением: Docker сам
атомарно назначает свободный порт через `127.0.0.1::target_port`, после чего
`duskrun` читает его через `docker inspect`, поднимает локальный SSH forward и
отдает дамперу обычный TCP endpoint `127.0.0.1:<local_port>`. После завершения
pipeline proxy-контейнер останавливается.

Если `duskrun` запущен прямо на том же Docker-хосте, можно использовать более
простой connector `docker-proxy` с полями `network`, `target_host`,
`target_port`; SSH-поля ему не нужны.
